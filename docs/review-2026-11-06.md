## User's objective

A custom interface for a Decent DE1 that preserves access to existing functionality
and remains easy to maintain. The user requested a plan for another agent covering
the entire review, including reuse of Streamline's settings.

## Architecture assessment and clarification

Keep the current architecture: an installable static skin, Decaid as the machine
and data backend, and an optional stateless AI server. The shared rules engine and
server-side TypeScript boundaries are useful foundations. A framework rewrite,
custom machine driver or fork of Decaid is not justified by this review.

Decaid skins supply substantial interfaces, not just colours. Streamline includes
its own settings, profile editor and shot-history presentation. An earlier explanation
in the review conversation incorrectly implied all those screens were native Decaid
screens. Do not carry that assumption into implementation. See the
[Streamline manual](https://github.com/decentespresso/streamline-js#readme).

The [Streamline Settings plugin](https://github.com/decentespresso/streamline-setting)
is a separately installable route to reusing its settings interface. It is not evidence
that a standalone profile editor or shot-history interface is included. Crema integration
and embedded-tablet navigation have not been tested.

## Findings and evidence

|---|---|---|---|
| R1 | Stop does not cancel a pending start | `skin/app.js`: `startOp`, `pushPresetSettings`, `renderControls`. Hold the settings promise pending, start steam, invoke the Stop handler's idle command, then resolve settings. Observed commands: `idle -> steam`. | Reproduced by executing the source in a Node VM with a controlled fake API; no physical machine involved. High priority. |
| R2 | Disconnection leaves stale readings and control state | `makeLiveApi.subscribe` only retries socket closure; it neither clears `S.snap` nor monitors machine connection state independently. | Confirmed source gap. Decaid documents that a machine disconnect can leave the socket open without frames. Physical behaviour untested. |
| R3 | Another device can invalidate the loaded recipe without Crema noticing | `S.loaded` is local; `startOp('espresso')` skips `apply` when true. No workflow read/subscription reconciles outside edits. | Source and fake-API check confirm start skips reapplication/revalidation. Two real clients not tested. |
| R4 | Profile browser omits installed custom profiles; fallback can recommend unavailable profiles | `makeLiveApi.catalog` maps only `E.CATALOG`. `rulesRecipe` uses `usable[0] ?? ranked[0]`. | Executed the committed engine with sample bean `results[0].info`: both `profileTitles: []` and `['My custom profile']` returned `Londonium`. Loading subsequently rejects that unavailable title. |
| R5 | Five-star ratings use the wrong storage scale | `makeLiveApi.feedback`, `annotate`, `toShot` and detail/history rendering pass enjoyment directly. | Calling the live adapter with five stars sends `{"annotations":{"enjoyment":5}}`; current Decaid uses 0–10. Existing high ratings can also display incorrectly. |
| R6 | Inventory and maintenance count incomplete history | `batchShots` and `maintenance.get` request `limit=500` without paging. Older reference shots can fall outside the UI's lookup window. |
| R7 | Additional bags overwrite bag-specific state | `saveBean` reuses matching roaster/name, creates a batch and replaces `bean:<id>` with recipe/reference reset; `shelf` picks one batch; `setBeanState` archives the bean. | Confirmed source behaviour. ## Scope of the recommendations

Required hardening, settings reuse, data corrections and release work are ordered in
the implementation plan. Feature gaps such as a new native profile editor, numeric
grind advisor and extra device support are inventory/discovery items, not automatic
authorization to build every feature mentioned in the parity document.
